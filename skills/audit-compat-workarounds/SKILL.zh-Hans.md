# 审查兼容补丁

默认对整个项目做只读审查。用户指定目录时，仅报告该目录内的发现。为解释某项发现，可查阅共用的依赖清单、调用方或支持策略。

## 找到兼容路径

- 先确认项目承诺读取哪些数据、在哪些环境运行、支持哪些构建工具。查看支持声明、导入与升级入口，以及各相关构建或发布目标实际选用的版本。
- 即使没有 `legacy` 或 `workaround` 注释，也要沿读取入口、API 适配层、平台或版本分支检查。遇到旧字段回退时，追踪哪个写入方曾生成旧格式，以及旧数据如今如何到达读取方。即使当前只写新格式，用户仍可能导入旧备份。
- 检查项目自己维护的源码、配置、构建脚本和依赖补丁。对补丁文件，从相关安装或构建入口追到补丁注册项或应用命令，核对它作用于哪个依赖版本。跳过第三方包内部由第三方维护的兼容实现。
- 遇到疑似绕行逻辑时，查清它解决的具体故障。回归测试、上游问题记录或代码历史都可能解释原因。只有证据能将延时、重试或默认值与某个具体缺陷或兼容要求联系起来时，才将其列入报告。

## 判断与报告

同一处补丁只报告一次，用 `文件:行号` 标出定义及读取、调用或应用入口。如果找不到入口，交代查过哪些位置。说明受影响的数据、接口、环境或具体缺陷，写明触发条件，从下表选择一项结论并附上依据。

| 结论 | 需要给出的依据 |
| --- | --- |
| 应保留 | 指出哪个受支持的目标仍受影响，或哪条受支持的导入、升级路径仍可能带入旧数据。 |
| 清理候选 | 说明触发条件为何已消失。对于上游已修复的缺陷，引用修复记录，并核实所有相关目标实际使用的版本均含修复。指出移除后应验证的行为。 |
| 待确认 | 已确认补丁用途，但仍缺少判断去留的事实。指明缺口，例如最早支持的备份格式，或由宿主提供的 SDK 版本。 |

报告末尾说明实际检查范围，以及哪些覆盖缺口会影响判断。零发现时，将结论限定在已检查的范围内。
