# 全项目审查

## 核心原则

- 把覆盖台账作为完成判定依据，不以抽样、印象或上下文耗尽代替全量覆盖。
- 默认只读指不改变被审查项目、持久用户状态或外部业务状态；允许把覆盖台账和临时证据写入系统临时目录。不要安装或升级依赖，不要切换、覆盖、回滚或清理工作区。
- 本技能只产出审查结果，不要自动扩展为修复流程；修改代码或把报告写入持久位置必须先取得用户明确授权。
- 先检查项目脚本及其配置，再决定是否运行；只执行已确认安全、非交互且与审查直接相关的命令。
- 不要读取 `.env*`、密钥或证书。默认不要主动检查、直接读取或输出登录态与浏览器缓存；用户明确授权后，只允许 Playwright 使用项目内 `.playwright/user-data`，仍禁止代理直接读取或披露其中内容。
- 为确定性结论提供可复查证据；证据不足时降级为待调查项或删除结论。
- 区分“全量完成”和“部分完成”；只要存在待审查、待调查、仅静态扫描、受阻或适用但未完成的运行时验证，就标记“部分完成”。

不要读取与当前项目形态无关的专项参考。

## 八步总控流程

### 1. 冻结快照

1. 定位仓库根目录，读取用户范围、仓库级及路径级指令和必要项目文档。
2. 默认以当前文件系统状态为审查快照，并纳入相关的已跟踪修改和未跟踪文件；用户指定 commit、分支或目录时，以该范围为准，但不要为了读取它而切换或覆盖工作区。
3. 记录审查时间、根目录、范围、当前分支、commit 和初始工作区状态；非 Git 项目记录探测到的根目录和范围边界。
4. 排除生成、缓存和大体积无关目录，例如 `node_modules`、`dist`、`build`、`.next`、`.nuxt`、`.output`、`coverage`、Playwright 报告、测试结果和包管理器缓存。
5. 除非任务明确涉及 SVG，否则忽略 `.svg` 文件；始终从文件搜索和语义审查中排除敏感文件及登录态目录。只有取得明确授权后，才允许 Playwright 通过持久上下文使用项目内登录态，代理不得直接检查其文件内容。

**完成门槛：** 明确记录可复现的快照标识、纳入范围、排除规则和初始工作区状态。

### 2. 建项目地图与覆盖台账

1. 识别包管理器、工作区、应用、包、框架、入口、路由、服务端边界、测试目录、构建配置、数据库边界和部署配置。
2. 为生产源码、共享库、框架入口、测试、质量门禁、配置、脚本、代码生成入口、Schema、迁移、路由、页面、API、依赖清单、锁文件和架构文档建立审查单元。
3. 为每个审查单元记录三个事实字段：范围处置为 `纳入` 或 `已排除` 并附理由；审查方式为 `未开始`、`语义审查`、`确定性工具验证` 或 `仅扫描`；“单元 × 适用维度”子状态为 `待审查`、`完成`、`不适用` 或 `受阻`。
4. 按事实字段派生唯一的展示用总体状态：范围外单元为 `已排除`；纳入范围且任一适用维度受阻时为 `受阻`；全部适用维度闭合后，按审查方式和单元类型派生 `已完成语义审查` 或 `已完成工具验证`；只做扫描时为 `仅静态扫描`；其余为 `待审查`。不要直接维护另一份可独立修改的总体状态。
5. 只有全部适用维度子状态均为 `完成`，或以具体理由标记 `不适用`，才能把源码、测试、配置或文档单元派生为 `已完成语义审查`；任一子状态待审查或受阻时，单元不得计入合格覆盖率。
6. 对源码、测试、配置和文档执行语义审查；只对锁文件等机器生成的结构化单元使用能覆盖完整内容的确定性工具。不要把文本搜索当作工具验证，也不要用工具验证替代源码语义审查。
7. 为排除项和受阻项记录原因。把覆盖台账放在系统临时目录；需要跨任务持久化时，先请求用户指定位置。
8. 当单次上下文无法可靠覆盖全部单元时，按工作区、领域或模块拆成不重不漏的批次，并在每批结束后更新台账。不要静默抽样。

**完成门槛：** 项目地图覆盖根级配置和全部工作区；每个单元都有范围处置，纳入范围的必需单元都有审查方式、所属批次、完整的“单元 × 适用维度”子状态及可复算的派生总体状态，且完成单元不存在未闭合子状态。

### 3. 执行安全诊断

1. 从锁文件确定现有包管理器，优先选择项目已有的 lint、typecheck、test 和 build 命令。
2. 在运行脚本前读取其实际命令和关联配置，判断是否联网、写源码或业务数据、更新快照、调用外部服务、迁移数据库或触发生命周期钩子。
3. 默认只运行已确认安全、非交互、与审查直接相关且不会写入目标项目、持久用户状态或外部业务状态的命令。任何可能生成构建产物、缓存、快照、浏览器资料或其他持久文件的命令，先取得用户对该写入的明确授权；未授权则标记受阻。
4. 不要安装或升级依赖，不要连接生产服务，不要执行迁移、seed、发布或可能写入业务数据的脚本。开发服务器只在确认绑定 `localhost` 或 `127.0.0.1`，且不会加载生产配置或连接生产服务后启动；若会写入项目目录，仍需先取得授权。
5. 对获授权的写入在命令前后比较工作区状态，披露生成或变化的路径；不删除审查前已有内容，也不擅自清理由命令生成的内容。
6. 把失败分类为代码失败、环境失败或依赖缺失，并记录命令、退出状态和可复查的错误摘要。长命令运行期间按宿主要求定期更新进度；只有确认超时或无进展时才停止。

**完成门槛：** 为每个适用诊断项记录“已运行及结果”或“未运行及原因”；任何不安全、未授权、环境受阻、依赖缺失或未完成验证都进入覆盖台账并触发部分完成。

### 4. 分派工作包

1. 使用审查矩阵把十个维度全部分配到工作包，不适用的维度记录具体原因。
2. 可使用子代理时，把互不依赖的只读审查组合为 3 至 4 个工作包并分波次执行；不要为十个维度机械创建十个代理。不可使用子代理时，按相同边界顺序执行。
3. 默认组合为：架构、正确性与数据边界；可维护性、废弃代码与依赖；性能、UI/UX 与可访问性；测试、构建、可观测性与安全基线。
4. 要求每个工作包返回“单元 × 适用维度”子状态、维度状态、候选发现、证据定位器和未验证项。拒绝只有笼统总结的结果。
5. 由主代理持续维护覆盖台账，检查工作包重叠与遗漏，并负责跨包验证、去重和最终状态判定。

**完成门槛：** 每个必需审查单元和适用维度都有明确负责人及返回状态；不存在未分派范围。

### 5. 运行 UI 验证

1. 仅对前端项目执行本步骤，并先清点全部路由，静态审查页面、布局、状态组件和关键流程。
2. 项目可安全运行、开发服务器只监听本机且已取得所需项目写入授权时，使用 Playwright 自带 Chromium 对可访问路由执行运行时冒烟验证，并对核心流程执行深度交互验证。不要使用系统 Chrome。
3. 默认使用无头模式、`1280x720` 视口和并发 1，并至少补充一个常见移动视口。检查可触达的成功、加载、空、错误和禁用状态，以及键盘操作和基础可访问性树。
4. 需要登录态时，必须先取得创建或更新持久浏览器资料的明确授权，再使用项目根目录下 `.playwright/user-data` 的持久上下文；若 `.playwright/` 未被忽略，还需单独取得修改 `.gitignore` 的授权。未获授权时把对应运行时验证标记受阻，不要读取或复用系统浏览器用户目录。
5. 不做全页截图；任务结束关闭页面和上下文。逐项记录因动态参数、权限、数据、后端或沙箱限制而受阻的路由。

**完成门槛：** 报告路由清点、运行时冒烟和核心流程覆盖率；只完成静态 UI 审查、部分运行时验证或存在受阻路由时，把总体状态标记为部分完成。

### 6. 验证发现

1. 按报告契约为每条候选发现补齐证据定位器、证据类型、影响、建议和验证方法。
2. 单文件内因果完整、可排除合理替代解释的确定性静态证据链，可以闭合语义审查；不要仅因证据类型是静态就自动记为受阻。
3. 为跨文件、运行时、框架行为或需要测量的定量结论提供第二种独立证据，例如调用链、配置、测试、构建输出、浏览器行为或当前官方文档；明确适用的运行时或测量验证未完成时记为受阻。
4. 不要仅凭“没有静态引用”判定框架约定入口、自动导入、动态导入、插件注册、反射调用、生成代码或公开包导出为废弃代码。
5. 把废弃代码结论分为已确认、高概率和待调查；只在排除约定、动态和公开接口后使用“已确认”。任何保留的待调查项都是未闭合候选，触发部分完成。
6. 把没有测量数据的性能、包体积和运行时收益标记为静态推断，不要写成实测改善。
7. 对版本、废弃 API、框架行为和迁移建议，优先通过 Context7 查询与项目版本匹配的当前官方文档；Context7 不可用时使用官方文档的当前版本。记录来源与适用版本，无法核验时降级置信度。
8. 只执行安全基线检查；不要把它描述为深度安全审计，也不要读取敏感文件或开展攻击性验证。需要深度审计时转交专门安全技能。

**完成门槛：** 每条确定性发现都满足统一字段契约和证据门槛；证据不足的项目只进入待调查或从报告删除。保留任何待调查项时，本步骤未完全闭合，总体只能是部分完成。

### 7. 合并排序

1. 按根因合并工作包结果，消除同一问题在不同文件、维度或症状下形成的重复项。
2. 对缺陷和风险使用 P0 至 P3；对优化和重构按收益、置信度、S/M/L 成本和回归风险排序。
3. 区分可用性或可访问性缺陷与审美建议，不要把个人偏好描述为缺陷。
4. 把结论放入“立即修复”“低成本高收益”“计划性重构”或“暂不处理或继续调查”行动档位。
5. 保留发现与审查单元、维度和证据之间的可追踪关系。

**完成门槛：** 每条发现都有唯一编号且无重复；优先级、置信度、成本、回归风险和行动档位一致。

### 8. 输出并判定完成

1. 默认在对话中输出结构化 Markdown，不要向目标仓库写入报告；仅在用户明确要求保存时创建文件。
2. 按报告契约依次输出执行摘要、项目与工作区地图、覆盖统计与盲区、命令结果、排序后的发现、行动路线、剩余风险和未验证事项。
3. 在报告开头明确写出“全量完成”或“部分完成”，并让状态与覆盖台账一致。
4. 只有在所有必需单元合格、所有适用维度完成、所有适用诊断项和运行时验证均完成、所有发现完成校验与去重、所有盲区已披露时，才标记“全量完成”。
5. 发现任一待审查、待调查、仅静态扫描、受阻、环境失败、依赖缺失、未完成命令或未完成运行时验证时，标记“部分完成”，列出剩余批次、受阻原因和继续方式。
6. 报告过长时先给出总数、覆盖状态和最高优先级摘要，再请求用户选择保存完整报告或继续分批输出。不要静默截断或只保留 Top N。
7. 没有经过验证的发现时，明确写出“未发现值得报告的问题”，同时保留覆盖、命令和盲区信息。

**完成门槛：** 报告字段完整、数量可核对、完成状态可由覆盖台账复算，且没有把静态推断、受阻项或安全基线夸大为已完成实测。

## 受阻处理

- 缺少依赖时，不要自动安装；继续静态审查，记录未运行命令并标记部分完成。
- 命令超时或确认无进展时，停止对应命令，记录已覆盖范围、失败分类和继续命令。
- 浏览器受沙箱限制时，降级为静态 UI 审查及安全可运行的类型、测试或构建验证，并标记部分完成。
- Monorepo 只有部分工作区可验证时，逐工作区记录状态；不要用其他工作区成功代替整体完成。
- 发现缺少证据时，降级为待调查项或删除；不要用推测填补字段。保留待调查项会使总体状态为部分完成。
- 临时覆盖台账不可用时，从项目地图重新生成；不要凭记忆补写完成状态。

## 全量完成检查表

只有以下项目全部满足时才声明全量完成：

- [ ] 已冻结并记录审查快照、范围和初始工作区状态。
- [ ] 已建立覆盖全部工作区、审查单元、路由和维度的台账。
- [ ] 所有必需单元及其“单元 × 适用维度”子状态均已闭合，且不存在待审查、仅静态扫描或受阻项。
- [ ] 所有适用维度均已完成；不适用维度均已记录原因。
- [ ] 所有适用诊断项与运行时验证均已完成并披露结果；不存在因不安全、未授权或环境限制而未运行的适用项。
- [ ] 所有候选发现均已校验、去重并满足报告字段契约，且不存在保留的待调查项。
- [ ] 已披露排除项、失败分类、盲区和运行命令前后的工作区状态。

任一项不满足时，输出“部分完成”。

## 常见失败

- 不要把文件清单、文本搜索或静态扫描当作语义审查完成。
- 不要把无静态引用直接等同于废弃代码，尤其不要误判 Nuxt 约定入口、动态插件和公开包导出。
- 不要在检查脚本内容前运行 test、build、迁移、代码生成或其他项目命令。
- 不要抽样后宣称全仓已审查，也不要因上下文不足静默丢弃剩余批次。
- 不要用单个工作区成功、单条命令通过或静态 UI 检查代表整体完成。
- 不要把性能推断描述为实测收益，也不要把安全基线描述为深度安全审计。
- 不要省略证据类型、置信度、成本、回归风险或验证方法，也不要让发现总数与实际输出不一致。
