## 使用规则

- 为每个维度记录 `完成`、`不适用` 或 `受阻`；为不适用和受阻状态写明原因。
- 把每个维度映射到具体工作区和审查单元，不要用仓库级笼统结论替代逐工作区覆盖。
- 只把符合本矩阵“完成标准”的维度记为完成；存在未审查范围，或任何适用且必要的验证因不安全、未授权、环境、依赖、权限、超时或沙箱原因未完整执行时，记为受阻。真正不适用的验证才排除，并记录具体原因。
- 使用文件与行号、工作区或模块、路由与元素、命令与结果、依赖条目或明确搜索范围作为证据定位器。

## 1. 项目结构、入口与模块边界

- **适用范围：** 对仓库根级配置、全部应用、包、工作区、生产入口、框架入口、路由入口和共享模块应用本维度。
- **检查重点：** 检查项目地图是否完整，检查目录职责、公开边界、依赖方向、循环依赖、跨层访问和根级与工作区级约定是否一致。
- **有效证据：** 接受清单文件、工作区配置、包导出表、框架配置、入口注册、导入链、路由表以及带行号的跨模块调用证据。
- **常见误报：** 不要把框架约定入口、配置驱动入口、自动发现目录、公开包导出或故意隔离的适配层仅因缺少普通 import 判为不可达或结构错误。
- **完成标准：** 仅在根级配置、全部工作区、入口、公开边界和关键依赖方向均已语义审查，并记录所有例外后标记完成。

## 2. 正确性、异常处理与可靠性

- **适用范围：** 对生产逻辑、异步流程、边界输入、资源生命周期、错误处理、并发与数据一致性路径应用本维度。
- **检查重点：** 检查输入验证、空值和边界条件、错误传播、重试与幂等、超时与取消、资源释放、竞态条件和失败后的状态一致性。
- **有效证据：** 接受可复查的控制流、调用链、数据流、类型诊断、单元或集成测试结果、运行日志以及可稳定复现的运行时行为。
- **常见误报：** 不要把经过明确不变量约束的路径、框架统一处理的异常、刻意快速失败策略或只在类型层不可能出现的状态当作实际缺陷。
- **完成标准：** 仅在关键成功路径、失败路径、外部边界和资源清理路径均已审查后标记完成。单文件内因果完整的确定性静态证据可闭合；跨文件、运行时或框架行为候选需要第二种独立证据或复现。

## 3. 可维护性、复杂度、重复与重构机会

- **适用范围：** 对所有生产源码、共享库、关键测试辅助代码和长期维护配置应用本维度。
- **检查重点：** 检查职责混杂、过深嵌套、过长数据流、隐式耦合、重复业务规则、命名歧义、难以测试的边界和可形成深模块的重构机会。
- **有效证据：** 接受带行号的重复实现、跨文件变更扩散路径、复杂控制流、频繁同步修改的接口、测试设置成本和具体维护场景。
- **常见误报：** 不要把小型局部函数、为避免错误耦合而保留的相似代码、生成代码或单纯不符合个人风格的写法直接判为重构问题。
- **完成标准：** 仅在全部生产模块完成语义审查，且每项建议都说明当前维护成本、预期收益、修改边界和回归风险后标记完成。

## 4. 垃圾代码、废弃代码、未使用依赖与过时 API

- **适用范围：** 对源码导出、路由、插件、中间件、脚本、依赖清单、公开包接口、代码生成入口和框架自动发现目录应用本维度。
- **检查重点：** 检查不可达代码、无消费者的内部导出、废弃分支、重复或失效资源、未使用依赖、过时 API 和残留迁移代码。
- **有效证据：** 对“已确认”结论同时提供无引用范围、入口与注册排除、动态机制排除、公开 API 排除和必要的构建或测试证据；对依赖结论同时检查源码、脚本、配置、类型、插件和工具链用途。
- **常见误报：** 不要仅凭无静态引用判定框架约定入口、自动导入、动态 import、字符串注册、反射调用、生成代码或公开包导出为废弃代码。不要把 Nuxt 的 `plugins/`、`.global` 中间件、约定路由、自动导入目录或工作区 `exports` 直接列为可删除项。不要把“不是最新版”本身判为问题。
- **完成标准：** 仅在排除约定入口、动态机制和公开接口后，把结论标记为 `已确认`；证据较强但仍需人工确认时标记 `高概率`；其余只标记 `待调查`。完成全部工作区的源码、配置和依赖用途核验，且不存在保留的待调查项后再标记本维度完成；保留待调查项时本维度受阻。

## 5. 前后端性能

- **适用范围：** 对前端渲染与水合、包体积、SSR、缓存、资源加载，以及后端 I/O、查询、并发、序列化和热点路径应用本维度。
- **检查重点：** 检查重复渲染、阻塞式工作、瀑布请求、过大客户端边界、缓存失效、N+1 查询、无界并发、重复序列化和缺少分页或背压的路径。
- **有效证据：** 优先接受性能剖析、构建产物分析、浏览器计时、查询计划、追踪数据、基准结果和稳定复现；只把源码与配置推导作为静态推断。
- **常见误报：** 不要把微观风格差异、未证明的树摇假设、缺少真实负载上下文的复杂度猜测或理论上的更快实现描述为已证实性能问题。
- **完成标准：** 仅在关键路由、渲染边界、数据获取和后端 I/O 路径均已审查，并明确区分实测结果与静态推断后标记完成。没有定量主张且未识别到必要测量时，完整静态审查可以闭合；已识别的适用测量未完成时记为受阻。没有测量数据时，不要声称已获得性能收益。

## 6. UI、交互、响应式与可访问性

- **适用范围：** 对所有前端路由、布局、页面、关键组件、可触达状态和核心用户流程应用本维度；纯后端项目记录不适用原因。
- **检查重点：** 检查视觉一致性、信息层级、交互反馈、键盘操作、焦点管理、语义结构、可访问名称、对比度、响应式布局以及成功、加载、空、错误和禁用状态。
- **有效证据：** 接受路由与元素定位器、组件行号、浏览器交互结果、可访问性树、键盘操作、局部截图和多个视口下的实际行为。
- **常见误报：** 不要把个人审美偏好、未触发的假想状态、刻意禁用的交互或无产品上下文的视觉替代方案描述为缺陷。
- **完成标准：** 仅在全部路由完成静态清点与运行时冒烟、核心流程完成深度交互，且不存在适用但受阻的路由或状态后标记完成；只做静态 UI 审查、部分运行时验证或存在受阻路由时，本维度记为受阻并使总体部分完成。

## 7. API、数据流、状态管理与服务端边界

- **适用范围：** 对公开和内部 API、服务端处理器、Schema、数据库访问、客户端状态、缓存、消息流和跨服务边界应用本维度。
- **检查重点：** 检查输入输出契约、权限边界、序列化、状态所有权、缓存一致性、事务边界、错误映射、重复请求和客户端与服务端职责分配。
- **有效证据：** 接受请求与响应 Schema、路由处理器、端到端数据流、数据库约束、事务代码、状态更新链、契约测试和实际请求结果。
- **常见误报：** 不要把有意的薄适配层、框架规定的数据加载方式、清晰的透传接口或只因分层偏好不同的设计判为边界缺陷。
- **完成标准：** 仅在全部暴露端点、关键内部边界、持久化路径和核心状态流完成语义审查，并核验异常与一致性路径后标记完成。

## 8. 测试覆盖、质量门禁与可测试性

- **适用范围：** 对测试目录、测试配置、质量脚本、CI 门禁、夹具、Mock 边界和生产代码的可测试性应用本维度。
- **检查重点：** 检查高风险行为是否有有效测试、测试是否验证真实行为、失败路径和边界条件是否覆盖、门禁是否实际执行，以及耦合是否导致测试困难。
- **有效证据：** 接受测试到需求或风险的映射、测试源码、配置、CI 工作流、覆盖报告、实际测试命令结果和可稳定复现的缺口。
- **常见误报：** 不要把行覆盖率等同于测试质量，不要因缺少某类测试就断言功能错误，也不要把刻意的集成边界或必要 Mock 自动判为坏设计。
- **完成标准：** 仅在全部测试套件、配置和门禁完成审查，所有适用测试验证均已安全完整执行并按风险说明缺口后标记完成；适用命令因不安全、未授权或环境限制未执行时，本维度记为受阻。

## 9. 构建、日志、可观测性与开发体验

- **适用范围：** 对根级和工作区级构建配置、类型检查、lint、CI、容器、部署配置、日志、指标、追踪和开发脚本应用本维度。
- **检查重点：** 检查构建一致性、缓存与增量边界、环境隔离、失败可诊断性、日志结构、关联标识、健康检查、告警信号和本地开发反馈周期。
- **有效证据：** 接受配置文件、脚本定义、CI 记录、安全执行的命令输出、日志调用链、指标与追踪接入点以及可复现的开发流程问题。
- **常见误报：** 不要把示例配置、环境专用差异、可选开发工具或没有运行环境证据的日志偏好直接判为生产问题。
- **完成标准：** 仅在根级和全部工作区配置均已语义审查，全部适用构建、类型、lint 与可观测性验证均已安全完整执行，且关键运行路径具备可诊断证据后标记完成；任何适用验证未执行时，本维度记为受阻。

## 10. 安全基线

- **适用范围：** 对常规源码和非敏感配置中的信任边界、认证授权、输入处理、输出编码、文件与网络访问、会话和明显凭证风险应用本维度。
- **检查重点：** 检查越权路径、注入源到汇、危险反序列化、路径穿越、开放重定向、不安全默认配置、敏感信息写日志和缺失的基础防护。
- **有效证据：** 接受完整源到汇调用链、权限检查路径、配置与使用点、测试或安全运行时行为，以及支持框架行为判断的当前官方文档。
- **常见误报：** 不要把公开标识符、测试夹具、占位值、无可达路径的危险 API 或纯理论攻击面直接判为漏洞；不要读取 `.env*`、密钥、证书或登录态来寻找证据。
- **完成标准：** 仅在全部已识别信任边界完成安全基线审查并披露盲区后标记完成。始终声明该维度不是渗透测试或深度安全审计；需要深入验证时转交专门安全技能。

## 跨维度证据规则

- 把证据类型标记为 `实测`、`静态推断` 或 `官方文档`；允许组合，但不要混淆强度。
- 单文件内因果完整、可排除合理替代解释的确定性静态证据可以独立闭合；为跨文件、运行时、框架行为或需要测量的定量结论提供至少两种相互独立的证据。
- 把文本搜索用作定位线索，不要把它单独用作语义完成证据。
- 把性能推断保留为静态推断，直到取得剖析、计时、构建分析或基准数据。
- 把安全基线限制在明显风险发现，不要把维度完成描述为深度安全审计完成。
