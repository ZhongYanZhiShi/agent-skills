# React 与 Next.js 审查参考

只在项目地图确认存在 React 或 Next.js 时读取本参考。它补充专项证据与误报边界，不替代总控流程、审查矩阵或报告契约。

## 先识别实际形态

1. 从清单、锁文件、框架配置和源码入口确认 React、Next.js、路由方案及实际版本，不根据目录名猜测。
2. 对 Next.js 区分 App Router、Pages Router 和混合迁移形态；同时记录 `src/`、`app/`、`pages/`、`public/` 及配置中的路径覆盖。
3. 清点页面、布局、模板、加载、错误、未找到、路由处理器、Server Actions、中间件、代理、动态段和并行或拦截路由等适用约定入口。
4. 记录渲染边界：服务端组件、客户端组件、服务端数据访问、浏览器 API、API 或路由处理器，以及第三方客户端组件。
5. 遇到缓存、路由约定、废弃 API、React/Next.js 版本差异或迁移建议时，先查询对应版本的当前官方文档，再形成确定性结论。

## React 语义审查

- **状态来源：** 查找同一事实的重复状态、可由 props 或现有状态直接派生却额外同步的状态，以及跨组件写入造成的不一致。
- **Effect 用途：** 确认 Effect 用于与外部系统同步。对只做派生计算、事件响应或同步状态链的 Effect，说明具体重复渲染或状态漂移路径后再建议移除。
- **生命周期：** 检查订阅、监听器、定时器、请求和外部实例是否在重跑与卸载时清理；检查竞态、过期闭包、取消和依赖变化。
- **列表与身份：** 检查 key 是否稳定且对应业务身份，避免索引或随机 key 导致状态错位；确认条件分支不会意外复用错误组件状态。
- **组件边界：** 检查巨型组件、跨层状态、过宽 Context、布尔属性膨胀和重复组合逻辑；重构建议必须说明变更扩散或测试困难等实际成本。
- **渲染性能：** 找出昂贵计算、无界列表、重复请求和高频状态更新。不要仅凭存在重渲染就建议 `memo`、`useMemo` 或 `useCallback`；需要 profiler、时间测量或明确的高成本调用链。
- **异步状态：** 检查成功、加载、空、错误、重试和取消路径，以及卸载后更新、重复提交和失序响应。
- **错误边界：** 检查关键子树或路由是否有与框架形态匹配的错误处理，但不要把每个小组件缺少独立边界列为问题。

## Next.js 专项审查

- **服务端与客户端边界：** App Router 中默认按服务端组件审查；确认 `'use client'` 只放在确需状态、事件或浏览器 API 的边界，避免把大子树无意推入客户端包。
- **序列化边界：** 检查跨服务端/客户端边界的 props、错误和数据是否可序列化，敏感值是否意外进入客户端输出。
- **数据获取：** 检查重复瀑布、顺序等待、缓存与重新验证意图、请求去重和失败策略。缓存行为随版本变化时必须以当前官方文档为证据。
- **路由处理器：** 检查输入验证、身份与权限、状态码、错误响应、幂等、超时、流式响应清理和缓存意图；不要把它当普通客户端 fetch 包装器略过。
- **Server Actions 与表单写入：** 清点模块级或内联的 `'use server'`、表单 `action` 和其他调用点，把每个 Action 视为独立写入边界；在 Action 内重新检查身份与资源级权限，不要依赖页面级守卫。检查 `FormData` 或参数的运行时验证、可序列化输入输出、幂等与重复提交、错误返回，以及写入后的 `revalidatePath`、`revalidateTag` 或重定向是否与缓存意图一致。
- **路由状态文件：** 检查 `loading`、`error`、`not-found` 等约定文件是否覆盖关键体验；缺失本身不是缺陷，必须结合实际等待、失败或导航行为说明影响。
- **动态路由：** 清点参数来源、静态生成范围、无效参数、权限和数据缺失路径；无法枚举或访问的实例计入受阻路由。
- **Pages Router：** 审查 `getServerSideProps`、`getStaticProps`、`getStaticPaths`、API routes 和 `_app`、`_document` 等实际入口；不要用 App Router 规则强行评判。
- **元数据与资源：** 检查关键页面标题、描述、规范 URL、字体、图片和脚本加载策略，但只报告有明确 SEO、性能或可访问性影响的项。
- **部署边界：** 检查 Node、Edge 或无服务器运行时假设、环境可用 API、持久连接、文件系统写入和进程内缓存是否与部署目标一致。

## 废弃代码与依赖误报边界

- 不要仅凭普通 import 搜索判定 `app/`、`pages/`、路由特殊文件、API route、middleware、配置文件或元数据文件未使用。
- 对 `dynamic()`、动态 `import()`、字符串组件表、MDX、插件注册、代码生成和测试装载建立单独证据链。
- 对组件库或包的公开导出，先检查 `package.json` 的 `exports`、文档、示例和仓库外消费者可能性；仓内无消费者最多支持“待调查”。
- 依赖用途同时检查源码、配置、CLI 脚本、编译插件、类型包、测试和构建链。只有排除这些入口后才报告未使用依赖。
- “客户端组件过多”“组件太大”或“缺少 memo”都不是独立证据；必须关联包体积、交互需求、渲染成本或维护扩散。

## 可接受证据

- 文件与行号、路由及对应特殊文件、服务端到客户端的导入链、构建或类型诊断、Profiler 或性能时间线、浏览器行为和网络请求。
- 对跨边界结论至少提供两类证据，例如源码调用链加构建输出、路由实现加运行时行为、配置加当前官方文档。
- 没有运行时或测量证据时，把水合、包体积、缓存和渲染收益标为“静态推断”，不要量化改善幅度。

## 完成门槛

只有同时满足以下条件，React/Next.js 专项维度才可标记完成：

- 已清点全部 React 入口和 Next.js 路由、特殊文件、路由处理器、Server Actions 及渲染边界；动态或受权限制的实例已逐类记录。
- 已语义审查适用的状态、Effect、异步、错误、服务端/客户端边界、数据获取、Server Actions 的授权、输入、写入与缓存边界，以及部署假设。
- 所有废弃代码与未使用依赖候选均已排除框架约定、动态机制和公开接口误报。
- 已完整运行适用且安全的类型、lint、测试、构建与 UI 验证；代码失败可作为已执行证据，但依赖缺失、环境失败、主动跳过或运行时验证缺失不满足本完成条件，并使总体状态为“部分完成”。
- 报告中的每条专项发现均含证据类型、定位器、置信度、影响、成本、回归风险和验证方法。
