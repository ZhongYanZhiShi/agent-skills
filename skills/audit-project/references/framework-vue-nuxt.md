# Vue 与 Nuxt 专项审查

仅在项目地图识别到 Vue 或 Nuxt 时加载本参考。继续使用总控技能的覆盖台账、审查矩阵与报告契约；本文件只补充 Vue/Nuxt 特有的审查单元、证据和误报边界。

## 识别版本与有效目录

1. 从 `package.json`、锁文件和框架配置交叉确认 Vue、Nuxt、构建工具及关键模块的实际版本，不要只根据目录名推断。
2. 判断是普通 Vue 应用还是 Nuxt 应用；Nuxt 项目记录主要版本、渲染模式、`modules`、`extends` 或 layers，以及是否自定义 `srcDir`。
3. Nuxt 4 默认以 `app/` 作为应用源码目录，Nuxt 3 通常以项目根为源码目录；兼容模式、旧目录探测和 `srcDir` 均可改变结果，因此必须以当前版本、`nuxt.config.*` 和实际目录共同确定有效应用根。
4. 同时记录 `srcDir`、`app/`、server、layers、modules 等目录的实际解析根，以及 layer 与工作区包的叠加关系；同名文件可能来自扩展层，不要只审查当前目录。
5. 把入口、路由、布局、组件、组合式函数、插件、中间件、服务端处理器、状态、配置和测试加入覆盖台账。

**完成门槛：** 已记录版本证据、有效应用根、目录形态、渲染模式和所有 layer 来源；任何无法确定项进入受阻或待调查，不得继续套用默认目录假设。

## Vue 响应式与组件边界

- 检查 `ref`、`reactive`、`computed`、`watch` 和 `watchEffect` 的数据所有权，确认解构、浅层响应式、原始对象逃逸或错误的 `.value` 使用不会丢失更新。
- `computed` 应保持可重复求值；其中存在写状态、网络请求、日志外的业务副作用或依赖时序时，沿调用链确认是否会重复执行或形成循环。
- 对 `watch` 与 `watchEffect` 检查依赖范围、`deep`、`immediate`、执行时机和停止条件。不要仅因存在 watch 就建议改写；只有纯派生状态且 `computed` 能保持相同语义时才提出简化。
- 检查异步监听中的竞态、过期响应和取消逻辑；依据项目 Vue 版本判断可用的清理 API，不要把新版本 API 直接建议给旧版本项目。
- 检查事件监听器、定时器、观察器、订阅和第三方实例是否随组件或 effect scope 清理；组合式函数还要核对多次调用时是否产生重复副作用。
- 检查 props、emits、`v-model`、slots 与 provide/inject 的契约，避免子组件直接修改父级所有权、事件与类型不一致、隐式全局依赖或跨层状态泄漏。
- 将渲染性能结论标记为静态推断，除非有 Vue Devtools、浏览器计时或稳定复现；不要把所有 computed、组件拆分或响应式更新都描述成性能问题。

## SSR 与客户端边界

- 检查模块顶层和服务端渲染路径中的 `window`、`document`、存储、媒体查询及仅浏览器可用的第三方库；确认其受客户端边界或生命周期保护。
- 检查服务端与客户端首次渲染是否依赖时间、随机数、视口、浏览器状态或顺序不稳定数据；没有运行时证据时只标记潜在水合风险。
- 检查 `.client`、`.server` 等文件边界、客户端专用组件和插件注册是否与调用位置一致，不要仅凭文件后缀判定安全或不可达。
- 检查请求级状态是否被模块单例、共享响应式对象或缓存泄漏到其他请求；同时核对服务端数据获取、缓存键和错误路径。
- 检查运行时配置的公开与私有边界，确认私有服务端值没有通过客户端 payload、日志或公开配置暴露；不要读取 `.env*` 获取证据。
- 对 SSR、预渲染、混合渲染和纯客户端模式分别判断适用规则；不适用项要记录原因，不能将 SSR 风险套用于明确关闭 SSR 的路径。

## 数据获取与共享状态

- 沿页面、组件、组合式函数和服务端入口追踪数据获取，检查请求是否重复、错误与空状态是否丢失，以及参数变化时旧响应是否覆盖新状态。
- 对 Nuxt 数据获取 API 检查 key、缓存、去重和服务端到客户端的数据传递；具体默认行为必须按项目版本查证，不要凭名称推断。
- 检查 `useState`、Pinia 或自建 store 的创建位置、请求隔离和序列化边界，避免服务端共享可变单例或把不可序列化对象送入客户端状态。
- 检查插件注入值和全局状态的类型、可用时机及服务端安全性；调用点缺少显式 import 不能作为未使用证据。
- 只有在请求链、渲染结果或测量数据证明重复获取、缓存错误或状态泄漏时才形成确定性发现；其余保留为静态推断。

## Nuxt 约定与自动发现

先根据有效应用根和版本清点下列约定入口；目录不存在时记录不适用，不要自行创建：

- `pages/`、`layouts/` 与入口文件形成路由和布局，文件可在没有普通 import 的情况下被使用。
- `components/`、`composables/`、`utils/` 可能由自动导入消费；还要检查自定义扫描目录、命名规则、动态组件和 `Lazy` 组件使用。
- `plugins/` 可自动注册并通过注入值消费；检查文件后缀、注册顺序和字符串访问，不能只搜索插件函数名。
- `middleware/` 包含命名、内联和全局中间件；核对路由元数据、命名转换和 `.global` 约定。
- `server/api/`、`server/routes/`、`server/middleware/` 及其他 server 目录由 Nitro 约定发现；检查路由映射、方法后缀和服务端调用链。
- Nuxt modules、hooks、配置注册、layers 和扩展目录可能增加路由、组件、插件或自动导入来源，必须纳入入口排除证据。

不要因为缺少普通 import 就把上述文件、自动导入符号、动态组件或注入值判为废弃。先证明文件不在有效扫描目录，且不存在配置、生成类型、路由、字符串注册、layer 或运行时消费者；仍无法排除时只能标记 `待调查`。

## 版本与官方依据

- 涉及目录默认值、自动导入范围、文件后缀、SSR 行为、API 废弃或迁移建议时，查询与已识别版本匹配的 Vue 或 Nuxt 当前官方文档。
- 报告记录官方来源与适用版本。无法获得当前文档或版本无法确定时，降低置信度，不得把记忆中的新版本行为作为确定性结论。
- “不是最新版”本身不是问题；只有存在已废弃 API、兼容性故障、安全影响或可证明的维护成本时才形成发现。

## 完成与报告

只有同时满足以下条件，才把 Vue/Nuxt 专项涉及的维度标记完成：

- 已识别版本、有效目录、渲染模式、配置、layers 与所有约定入口，并在覆盖台账中逐项有状态。
- 已语义审查响应式数据流、组件契约、副作用清理、SSR/client 边界、数据获取和服务端入口。
- 已对所有废弃候选排除自动发现、动态注册、注入、路由约定与外部公开接口，并按证据分级。
- 所有适用且安全的类型、测试、构建或运行时验证均已完整执行；代码失败可作为已执行证据，但无法执行、依赖缺失、环境失败或主动跳过不满足本完成条件，必须标记受阻。

除报告契约的通用字段外，每条 Vue/Nuxt 发现还要在证据中注明：适用版本、有效应用根或 layer、涉及的约定机制、SSR/client 运行边界，以及该审查单元的验证状态。任一完成条件未满足时，相关维度记为受阻，总体只能是“部分完成”。
