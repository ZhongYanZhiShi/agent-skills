# Monorepo 专项审查

仅在仓库存在工作区声明、多包清单或现有任务编排时加载本参考。继续使用总控技能的覆盖台账、审查矩阵与报告契约；本文件只规定多工作区的范围、包图、验证和误报边界。

## 识别工作区与编排

1. 从根 `package.json`、`pnpm-workspace.yaml`、锁文件和其他现有清单交叉识别 npm、pnpm 或 Yarn workspaces；不要仅凭 `apps/`、`packages/` 目录名认定 Monorepo。
2. 展开 workspace 包含与排除规则，记录每个实际工作区的路径、包名、版本、`private` 状态、角色和主要技术栈；重复包名、未匹配路径和嵌套清单单独记录。
3. 检查 `turbo.json`、`nx.json`、`project.json` 或现有脚本，识别 Turbo、Nx 及其他真实存在的任务编排。没有配置时不要假设使用某种编排器。
4. 记录根级 package manager、锁文件边界、共享配置、CI、发布配置和代码生成入口。存在多个锁文件或包管理器时先确认它们是否对应隔离子项目，再判断是否为漂移。
5. 不要自动运行安装、迁移、发布、版本提升或代码生成命令；所有验证仍遵守总控技能的安全诊断边界。

**完成门槛：** 已解析全部工作区规则，根级配置和每个匹配工作区都进入项目地图与覆盖台账；未知、未匹配或不支持的工作区记为受阻，不得静默排除。

## 建立包图与公开边界

- 为每个工作区记录 `dependencies`、`devDependencies`、`peerDependencies` 和 `optionalDependencies` 中的内部包边，并区分运行时、构建、开发和对等依赖。
- 识别 `workspace:` 等本地协议、TypeScript project references、路径别名、源码深层导入、CLI `bin`、代码生成和配置字符串引用；不要只依赖清单中的普通依赖边。
- 检查 `exports`、`imports`、`main`、`module`、`types`、`browser`、`bin` 和公开子路径，建立“公开入口—实现—仓内消费者”映射。
- 对共享包记录其预期消费者和发布边界。应用包、工具包、配置包、类型包和可发布库的合理依赖方向不同，不要套用固定分层偏好。
- 检查消费者是否绕过公开入口深层导入源码，路径别名是否掩盖未声明依赖，以及构建产物、类型声明和条件导出是否对齐。
- 分别检查清单依赖图、源码导入图和任务图中的循环；只有给出完整环路和实际影响时才形成确定性发现。

## 低误报的废弃判断

- 公开 `exports`、子路径、`bin` 或可发布包可能被仓库外消费者使用，不能仅凭仓内无消费者判为废弃。
- `private: true` 只能证明包不应直接发布，不能证明其入口无用；还要排除 CI、脚本、配置、动态加载、测试、代码生成和部署消费者。
- 没有普通 import 的配置包、ESLint/TypeScript 预设、构建插件、Nuxt module 或 CLI 可能通过字符串和工具配置使用，必须检查相应配置与脚本。
- 对内部导出，先核对包公开边界、源码和生成入口，再给出 `已确认`、`高概率` 或 `待调查`；无法排除外部消费者时不得标记 `已确认`。
- 未使用依赖需要同时检查全部工作区源码、脚本、配置、类型、插件和工具链；根依赖可能服务多个工作区，不能按单包搜索结果删除。

## 逐工作区验证

1. 枚举根级和每个工作区已有的 lint、typecheck、test、build 等脚本，记录脚本缺失与继承关系。
2. 检查根脚本、Turbo pipeline 或 Nx target 实际覆盖哪些工作区、依赖任务、输入、输出与过滤条件；命令成功不等于所有包都执行过。
3. 优先使用能明确报告包级结果的现有根编排命令；根命令无法证明完整覆盖时，再使用现有包管理器的 workspace/filter 能力逐包执行安全脚本。
4. 不虚构工作区缺失的脚本，也不为统一命令而修改配置。脚本不存在时审查其影响，并在工具验证项中记录未运行原因。
5. 每次验证记录工作区、实际命令、退出状态、失败分类、被跳过包和缓存命中信息；缓存命中只有能证明对应输入与产物有效时才算完成。
6. 单个工作区受阻、未执行或只完成静态扫描时，该工作区不计入合格覆盖率，仓库总体标记“部分完成”。

## 依赖、版本与边界漂移

- 比较内部包协议、同一外部依赖的版本范围、peer 约束、运行时单例要求、TypeScript 和框架版本，以及共享配置的适用范围。
- 版本不同本身不是问题。只有造成重复运行时、peer 冲突、构建差异、类型不兼容、补丁遗漏或明确维护成本时才形成发现。
- 检查根级依赖提升是否让工作区依赖未声明也能通过，锁文件是否与清单一致，以及发布包是否遗漏必要依赖或错误携带开发依赖。
- 检查跨层依赖是否违反仓库已有边界规则；没有规则时根据包职责和真实调用链说明影响，不凭个人目录偏好下结论。
- 涉及 workspace 协议、Turbo/Nx 行为、版本兼容或废弃配置时，查询与已识别版本匹配的当前官方文档；无法核验时降低置信度。

## 任务图与发布证据

- 检查任务依赖、输入、输出、环境变量声明和缓存边界是否与真实读写一致；缓存命中不能证明错误配置下的任务有效。
- 区分全仓任务与 `affected`、filter 或变更集任务。增量任务只证明其实际选择的工作区，不得替代未执行包的全量验证。
- 检查包构建顺序、类型生成和产物消费关系；源码可直接运行不代表发布产物、类型声明或条件导出可用。
- 对可发布包核对打包文件范围、公开入口和版本关系，但不要执行 publish、pack、版本提升或发布生命周期脚本。
- CI 矩阵、发布配置和部署清单可以证明仓外消费者或特殊任务路径；没有仓内 import 时仍需纳入废弃判断。
- 任务图或发布行为依赖工具版本时，使用当前官方文档作为第二证据；无法安全执行时标记受阻，不以配置阅读冒充实测。

## 部分完成规则

- 某工作区因技术栈、权限、依赖或环境无法语义审查时，将它保留在工作区分母并标记受阻；继续审查其他包，但总体只能是“部分完成”。
- 配置包、工具包和示例包仍需审查其真实职责；只有审查矩阵中的具体维度确实不适用时，才能逐维度记录不适用。
- 根编排命令遗漏、过滤或跳过的工作区，只有通过等价的逐包验证后才能计入工具覆盖率，否则记录未完成项和继续命令。

## 完成与报告

只有同时满足以下条件，才把 Monorepo 专项涉及的维度标记完成：

- 根级配置、所有解析出的工作区和共享工具配置均已语义审查，且每个工作区都有唯一状态。
- 包图覆盖清单依赖、源码跨包引用、公开导出、内部消费者、任务依赖和已识别的发布边界。
- 每个工作区的适用且安全脚本均已完整执行并记录结果；代码失败可作为已执行证据，但受阻、未执行或被根命令跳过的包不满足本完成条件。
- 依赖与版本漂移、循环依赖、深层导入、未声明依赖和跨层边界均已检查，候选发现已经证据分级。

除报告契约的通用字段外，每条 Monorepo 发现还要在证据中注明：工作区或包名、包角色、依赖边或任务边、公开/私有及导出子路径、受影响消费者、验证命令与工作区状态。任何工作区或根级必需单元未完成时，工作区覆盖率必须保留该项在分母中，总体只能是“部分完成”。
