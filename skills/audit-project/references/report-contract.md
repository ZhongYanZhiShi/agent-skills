## 运行状态

### 全量完成

只有同时满足以下条件时，才在报告标题后的第一行标记 `全量完成`：

- 让所有范围内必需审查单元按类型完成语义审查或确定性工具验证，并让其全部“单元 × 适用维度”子状态闭合。
- 确保不存在 `待审查`、`仅静态扫描` 或 `受阻` 单元。
- 让所有适用维度完成，并为每个不适用维度记录原因；确保不存在受阻维度。
- 确保不存在保留的 `待调查` 候选；待调查表示证据尚未闭合，不满足全量完成。
- 完成所有适用诊断项：只执行已确认安全且获得必要写入授权的命令，并记录命令、结果和工作区影响；不存在因不安全或未授权而跳过的适用项。
- 对前端项目完成适用的路由运行时冒烟和核心流程验证，确保不存在未完成运行时验证。
- 校验并去重全部候选发现，披露排除项、命令结果和盲区。

代码检查、测试或构建命令以非零状态结束时，只要命令已安全完整执行并记录结果，就把它作为发现证据，不要自动把覆盖率记为未完成。命令因不安全、未获写入授权、环境、依赖、权限、超时或沙箱原因无法完整执行时，把对应项记为受阻并标记部分完成。

### 部分完成

出现以下任一情况时，在报告标题后的第一行标记 `部分完成`：

- 存在待审查、仅静态扫描或受阻单元。
- 存在未完成或受阻维度。
- 存在因不安全、未授权或其他原因未运行的适用验证命令、依赖缺失、环境失败或未完成运行时验证。
- 只完成静态 UI 审查、只覆盖部分路由、只审查部分工作区或只输出部分批次。
- 尚未完成发现校验、去重或统一字段补全。
- 保留任何 `待调查` 候选或低置信度调查线索。

在部分完成报告中列出剩余批次、每个受阻原因、已覆盖范围和可直接继续的方式。不要使用“基本完成”“大致全量”或其他模糊状态替代这两个状态。

## 覆盖率口径

先固定分母，再开始审查。对每项同时报告 `分子/分母`、百分比、排除数和受阻数；分母为零时报告 `不适用`，不要报告虚假的 100%。

### 审查单元合格覆盖率

使用以下公式：

`审查单元合格覆盖率 = 合格审查单元数 / 范围内必需审查单元总数 × 100%`

按单元类型判断“合格”。覆盖台账必须记录范围处置、审查方式和“单元 × 适用维度”子状态。总体状态只由这些事实派生：范围外为 `已排除`；任一适用维度受阻为 `受阻`；全部适用维度闭合后按单元类型与审查方式派生 `已完成语义审查` 或 `已完成工具验证`；只做扫描为 `仅静态扫描`；其余为 `待审查`。只有全部适用维度子状态均为 `完成`，或以具体理由标记 `不适用`，单元才可进入分子：

- 只把完成语义审查的源码、测试、配置和文档计入分子。
- 只把被确定性工具完整覆盖的锁文件等机器生成结构化单元计入分子。
- 不把文本搜索、文件清点、仅静态扫描、待审查或受阻单元计入分子。
- 把有明确理由的范围外排除项放到分母之外，并单独列出；不要用排除掩盖受阻项。

证据类型是“静态推断”本身不会自动阻止单元合格：单文件内因果完整的确定性静态证据可以闭合语义审查；跨文件、运行时、框架行为或定量结论仍需满足第二证据及适用验证门槛。

### 源代码语义覆盖率

使用以下公式：

`源代码语义覆盖率 = 已完成语义审查的源代码单元数 / 范围内源代码单元总数 × 100%`

统一按文件或预先定义的模块单元计数，并在报告中说明计数基准。不要在同一报告中混用文件数、目录数和代码行数。

### 工具验证覆盖率

使用以下公式：

`工具验证覆盖率 = 已完整执行并记录结果的适用工具验证项数 / 适用工具验证项总数 × 100%`

把预先识别的 lint、typecheck、test、build、确定性结构校验和其他诊断作为工具验证项。把完整执行后的成功或代码失败都计入分子；适用但因不安全、未授权、环境失败、依赖缺失、权限受阻、超时未完成或主动跳过的项目保留在分母中，不计入分子。真正不适用的项目才排除并说明原因。

### 工作区覆盖率

使用以下公式：

`工作区覆盖率 = 合格工作区数 / 范围内工作区总数 × 100%`

只有当某工作区的必需单元均合格、适用维度均完成且适用工具验证均已完整执行时，才把该工作区计为合格。不要用根工作区或其他包的成功替代受阻工作区。

### 维度覆盖率

使用以下公式：

`维度覆盖率 = 已完成适用维度数 / 适用维度总数 × 100%`

把有明确原因的 `不适用` 维度排除在分母外并单独列出。把受阻维度留在分母中，不计入分子。

### 前端路由覆盖率

对每个前端应用分别报告以下三项，并汇总仓库级结果：

- `路由清点覆盖率 = 已清点并完成静态审查的路由模板数 / 已识别路由模板总数 × 100%`
- `运行时冒烟覆盖率 = 已完成浏览器冒烟的路由模板数 / 已识别路由模板总数 × 100%`
- `核心流程覆盖率 = 已完成深度交互验证的核心流程数 / 已识别核心流程总数 × 100%`

仓库级结果按指标分别累加各前端应用的分子与分母，再用分子总和除以分母总和；禁止直接平均各应用百分比。某应用的指标分母为零时，将该指标记为不适用并从仓库级分母中排除，同时说明原因。

主路由指标统一以路由模板计数。每个动态模板预先记录代表实例及状态；只有该模板计划的代表实例全部完成，模板才计入运行时分子。参数、权限、数据、后端或沙箱导致受阻时，把模板保留在分母中并逐项列出。需要时可另报实例级覆盖率，但不得与模板级分子、分母混用。

## 报告结构

按以下顺序输出结构化 Markdown：

1. 在标题后立即写出 `全量完成` 或 `部分完成`。
2. 输出执行摘要，说明范围、快照、总体结论和最高优先级行动。
3. 输出项目与工作区地图，列出应用、包、框架、入口和服务端边界。
4. 输出覆盖统计、单元状态、维度状态、排除项和盲区。
5. 输出已运行及未运行命令，记录结果、失败分类和工作区影响。
6. 按优先级输出经过验证的发现，并保留唯一编号。
7. 输出行动路线，分为立即修复、低成本高收益、计划性重构、暂不处理或继续调查。
8. 输出剩余风险、未验证事项、剩余批次和继续方式。

默认在对话中输出报告。只有用户明确要求保存时才写入文件，不要默认修改被审查仓库。

## 发现字段契约

为每条发现使用以下字段，禁止省略：

```markdown
### [编号] [标题]

- 类别：[十个审查维度之一；必要时补充“缺陷/风险/优化/重构/待调查”]
- 严重度或收益：[P0/P1/P2/P3，或高/中/低收益]
- 置信度：[已确认/高/中/低]
- 证据定位器：[文件:行号、工作区/模块、路由/元素、命令/结果、依赖条目或明确搜索范围]
- 证据类型：[实测/静态推断/官方文档；允许组合]
- 影响：[描述受影响对象、触发条件和后果]
- 建议：[给出直接、可执行且与根因对应的处理方式]
- 成本：[S/M/L]
- 回归风险：[高/中/低；注明主要回归面]
- 验证方法：[给出修复后可执行的测试、命令、浏览器步骤或测量方式]
```

让编号在整份报告中唯一且稳定。对缺失项使用明确的“无法确定”并把置信度降级；不要用猜测填充字段。低置信度结论只能进入待调查区，不要混入确定性发现；任何保留的待调查项都会使总体状态为部分完成。

## P0 至 P3

- **P0：** 只用于正在造成或极可能立即造成灾难性故障、数据损失、关键安全影响或大范围不可恢复中断的问题；要求直接实测或完整证据链。
- **P1：** 用于高影响、高发生概率或关键路径失效且应优先处理的问题。
- **P2：** 用于中等影响、范围受限、具有可靠规避方式或需要特定条件触发的问题。
- **P3：** 用于低影响、局部质量、轻微可用性或长期维护问题。

对优化与重构使用 `高/中/低收益`，不要为非缺陷强行分配 P 级。把 UI 审美建议与可用性、可访问性缺陷分开。

## 置信度

- **已确认：** 要求实测复现、确定性工具结果，或足以排除合理替代解释的完整静态证据链。
- **高：** 要求至少两项相互支持的证据，且没有发现有效反证，但仍缺少直接复现或最终环境确认。
- **中：** 使用一项较强静态证据和清晰影响路径，但保留需要验证的关键假设。
- **低：** 只形成合理线索，证据不足以作确定性判断；只放入待调查区。

不要仅凭无静态引用把框架约定入口、动态导入或公开包导出赋予高置信度废弃结论。

废弃代码证据等级映射到统一字段时使用：`已确认` → `置信度：已确认`；`高概率` → `置信度：高`；`待调查` → 补充 `类别：待调查`，并根据剩余假设使用 `置信度：中` 或 `低`。不要把三档名称直接写进不接受该值的字段；保留待调查项时总体只能是部分完成。

## 成本与回归风险

- **S：** 用于局部修改，通常限制在单个文件或紧邻位置，且不改变跨模块契约。
- **M：** 用于跨文件或单模块修改，可能需要更新测试、配置或内部接口。
- **L：** 用于跨模块、跨工作区、数据迁移、公开 API 或架构级修改。

不要给出缺乏团队和发布上下文的精确工时。把回归风险标为高、中或低，并注明受影响的接口、数据、路由、工作区或部署路径。

## 长报告分批规则

预计完整报告超出单次对话可靠长度时：

1. 先输出运行状态、总发现数、各优先级数量、覆盖率、盲区和最高优先级摘要。
2. 列出所有批次的范围、发现数量和输出状态，让总数可核对。
3. 请求用户选择把完整报告保存到指定位置，或按明确批次继续输出。
4. 继续输出时保持编号稳定，并在每批标明已输出数与剩余数。

不要静默截断，不要只保留 Top N，不要让摘要总数与实际输出失去对应关系。

## 零发现规则

没有经过验证的发现时，明确写出：`未发现值得报告的问题`。

仍然输出运行状态、范围、覆盖率、命令结果、排除项、盲区和未验证事项。不要为了填满维度或证明工作量而制造建议。部分完成且零发现只表示“已覆盖部分未发现问题”，不要暗示未覆盖范围没有问题。

## 最终一致性检查

提交报告前逐项检查：

- [ ] 让标题后第一行的运行状态与覆盖台账一致。
- [ ] 让所有覆盖率都能由分子、分母、排除数和受阻数复算。
- [ ] 让每条发现包含全部必填字段、唯一编号和可复查定位器。
- [ ] 确认不存在被错误计入全量完成的待调查项。
- [ ] 让 P0 至 P3、收益、置信度、成本和回归风险符合定义。
- [ ] 把性能静态推断与实测数据分开。
- [ ] 把安全基线与深度安全审计分开。
- [ ] 让发现总数、分批数量和实际输出数量一致。
- [ ] 在零发现时保留覆盖和盲区，不制造填充项。
