# UI 运行时审查参考

全量范围包含前端应用时读取本参考；只有用户明确排除 UI 维度时才跳过并披露范围调整。运行时验证用于补充静态语义审查，不能代替页面、布局和状态组件的源码审查。

## 1. 建立路由与流程台账

1. 从框架约定目录、路由配置、导航、重定向和产品文档清点路由，不只依赖首页可见链接。
2. 为每条路由记录静态路径或动态模板、所属布局、权限、数据前置条件、关键状态和是否属于核心流程。
3. 将动态路由按模板和代表性参数实例记录；主覆盖率始终按模板计数，代表实例另记状态。无法安全取得参数时把该模板标记受阻，不虚构 URL。
4. 从入口、导航和业务代码识别核心流程，例如登录、搜索、创建、编辑、删除确认、结账或管理操作；只选择项目实际存在的流程。
5. 分开记录路由清点、运行时冒烟和核心流程深度验证，不能用其中一项替代另一项。

## 2. 判断能否安全启动

- 先读取 `package.json`、锁文件、启动脚本、框架配置和必要代理配置，确认命令不会安装依赖、写业务数据、连接生产环境或执行生命周期副作用。
- 不读取 `.env*`。若无法从非敏感配置确认服务目标安全，停止运行时启动并降级为静态审查。
- 不自动安装或升级项目依赖。现有依赖不完整、后端缺失或构建失败时，记录环境失败或依赖缺失。
- 开发服务器只绑定 `localhost` 或 `127.0.0.1`，使用可预测端口；仅在确认不会加载生产配置、连接生产服务或写入外部业务状态后启动，并保留启动命令、端口、进程状态和关闭结果。
- 若开发服务器会在目标项目中生成 `.next`、`.nuxt`、缓存或其他文件，先取得用户对这些写入的明确授权；未获授权时降级为静态审查并标记受阻。
- 运行前后比较工作区状态；不要删除已有文件或擅自清理由命令产生的内容。

## 3. Playwright 执行边界

- 必须优先使用 Playwright 自带 Chromium；不要设置 `channel: "chrome"`，不要指定系统 Chrome 的 `executablePath`。
- 默认保持 `headless: true`、视口 `1280x720`、并发 1；再使用一个常见移动视口复查响应式行为。
- 若项目已有 Playwright 但缺少 bundled Chromium，先取得用户授权与宿主批准，再运行 `pnpm exec playwright install chromium`；这不授权安装或升级项目包。
- 不需要登录态时使用隔离的普通 context。需要保持 Cookie、localStorage、IndexedDB 或缓存时，使用 `chromium.launchPersistentContext()`。
- 持久上下文的 `userDataDir` 只能是项目根目录下 `.playwright/user-data`；不得读取或复用系统 Chrome 用户目录。
- 获得授权后只允许 Playwright 通过持久上下文使用该目录；代理不得直接打开、搜索、提取或输出 Cookie、Token、localStorage、IndexedDB 或其他登录态内容。
- 创建或更新持久目录前，先取得用户对持久浏览器资料写入的明确授权，并确认 `.playwright/` 已在 `.gitignore`。若未忽略，还需单独请求修改 `.gitignore` 的授权；任何一项未获授权都使登录态验证受阻。
- 首次确需扫码、验证码或人工登录时，可在取得 GUI 授权后临时使用 `headless: false`；登录完成后恢复无头模式。
- 不做 `fullPage` 截图。只在证据确有必要时读取局部 DOM、可访问性信息、网络状态或截取局部元素。
- 每次任务结束关闭已创建的 page、context 和 browser；使用持久上下文时关闭 context 即可关闭浏览器。

## 4. 路由冒烟验证

对每个无需缺失权限或数据即可访问的路由，至少检查：

- 页面是否到达预期路由，是否出现白屏、错误边界、重定向循环或明显布局破坏。
- 页面标题、主标题、主要区域和首要操作是否存在且语义合理。
- 控制台是否出现未处理异常、水合错误或重复严重警告；网络是否存在关键资源或 API 失败。
- 初始焦点、跳转后焦点和键盘 Tab 顺序是否可用，交互元素是否有可识别名称。
- 桌面与移动视口是否出现内容溢出、遮挡、不可达操作、异常横向滚动或触控目标过密。

不要把第三方脚本噪声、开发模式提示或单次网络抖动直接列为产品缺陷。先复现并定位到项目代码或配置。

## 5. 核心流程与状态验证

- 对每个核心流程验证入口、主路径、校验失败、取消或返回、重复提交保护和成功后的状态一致性。
- 覆盖实际可触达的加载、空、错误、禁用、只读和权限不足状态；无法构造的状态写入受阻项，不通过改业务数据强行触发。
- 检查键盘可完成性、焦点可见性、对话框焦点约束与恢复、Escape 行为，以及状态变化是否对辅助技术可感知。
- 检查表单 label、错误关联、必填状态、自动完成、提交中反馈和错误保留；不要只依据视觉占位符判定可访问名称。
- 检查颜色对比、动效、缩放和响应式时，优先使用计算样式、可访问性树和可复查截图；审美偏好单独标为建议。
- 涉及删除、支付、发送消息、生产写入或其他外部副作用时，不执行真实提交；验证到安全边界并记录未完成步骤。

## 6. 证据与误报控制

- 运行时发现至少记录路由、视口、前置条件、操作序列、预期与实际结果、复现次数和源码定位器。
- 证据可包括局部截图、DOM 或可访问性属性、控制台摘要、失败请求、视频片段或对应组件代码；不要保存登录态或敏感响应。
- 自动可访问性扫描只能作为候选来源。对可操作性、阅读顺序、名称或焦点问题进行人工语义验证后再报告。
- 不因像素差异、个人风格偏好、第三方组件默认样式或单一视口观察就宣称 UI 缺陷。
- 无法稳定复现的问题降低置信度；只有静态源码依据时标记“静态推断”。

## 7. 覆盖计算与完成门槛

- **路由清点覆盖率：** 已纳入台账并完成静态审查的路由模板数 ÷ 已识别路由模板总数。
- **运行时冒烟覆盖率：** 计划代表实例均已完成冒烟的路由模板数 ÷ 已识别路由模板总数。
- **核心流程覆盖率：** 已完成深度验证的核心流程数 ÷ 已识别核心流程总数。
- 模板级分母、排除项、动态实例选择和受阻原因必须可核对；权限、数据、后端或沙箱导致的受阻模板仍留在分母中，不能删除受阻项来提高覆盖率。需要时另报实例级覆盖率，但不要混入模板级指标。
- 只有路由台账完整、所有已识别路由模板的计划代表实例均已冒烟、核心流程和关键状态已验证、桌面与移动视口已覆盖、浏览器资源已关闭且证据完整时，UI 运行时维度才可标记完成。
- 项目无法安全启动、浏览器受限、登录或数据缺失、存在未验证路由或核心流程、只完成静态审查时，总体状态必须为“部分完成”。
