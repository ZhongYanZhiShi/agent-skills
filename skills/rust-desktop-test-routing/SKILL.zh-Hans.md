# Rust 桌面测试路由

按真正运行被改动行为的表面来路由验证。本技能要防止的常见失败是：对一个不完整的 Rust 桌面
应用网页构建启动浏览器测试，并在原生运行时从未被实际执行的情况下报告成功。

## 选择任何命令之前

先检查项目再决定如何验证：

- 项目说明（AGENTS.md 或等价文件）与已记录的测试、验证约定；
- 能揭示框架与目标的清单和构建文件（Tauri、Wry、egui、iced、Slint、GPUI，或普通库/二进制/CLI）；
- 包和工作区脚本及 CI 配置，复用项目已经使用的命令；
- 受影响的文件及其所属层；
- 现有测试套件，选取已经覆盖该层的最小测试。

如果改动没有触及原生桌面目标，则不适用本技能。

## 对改动行为分类

把改动归入以下类别之一：

1. **纯 Rust 逻辑**——与框架无关的逻辑、算法、解析、数据结构或状态转换，从不跨越操作系统、
   WebView、IPC 或渲染器。
2. **浏览器完备的渲染行为**——完全在 WebView/HTML 层内运行的 UI，不涉及原生桥接、IPC、
   文件系统或数据库，也没有仅桌面才有的状态。
3. **桌面原生集成**——任何触及操作系统或原生运行时的行为：IPC、WebView 初始化、文件系统、
   数据库持久化、对话框、菜单、托盘、窗口管理、生命周期、重启恢复、单实例、事件循环、原生
   输入或渲染。
4. **混合行为**——跨越多个类别的改动。

## 为所属层选择最小测试

- 对于**纯 Rust 逻辑**，运行覆盖该逻辑的最小现有单元或集成测试。通过的单元测试只证明逻辑，
  永远不能证明原生表面。
- 对于**浏览器完备的渲染行为**，浏览器测试可以作为最终验收——但仅针对完全无需原生桥接、
  模拟或仅桌面状态即可用的具体行为。
- 对于**桌面原生集成**，浏览器证据最多只是辅助。它可以确认渲染侧，但无法证明原生运行时可用。
- 对于**混合行为**，按所属层拆分验证。每一层都需要自己的证据，单层通过不能代替其他层验收。

## 判断浏览器证据何时算数

仅当以下条件全部满足时，才把 Playwright/浏览器测试作为最终验收：

- 受影响行为被归类为浏览器完备的渲染行为；
- 它在无原生桥接、模拟或仅桌面状态的情况下完整运行；
- 项目已经为此目的使用该浏览器测试工具。

对于涉及 IPC、WebView 集成、文件系统、数据库持久化、对话框、菜单、托盘、窗口、生命周期、
重启恢复、单实例、事件循环、原生输入/渲染或操作系统集成的任何内容，浏览器证据只是辅助——
对渲染器有帮助，但不是原生表面的证明。

## 桌面验收需要原生证据

对于桌面原生集成，验收需要原生测试或真实桌面执行：项目自身的原生测试工具、驱动真实运行时的
集成测试，或运行桌面应用并实际执行该行为。如果没有这样的路径，应将原生行为报告为**受阻**
或**未验证**——绝不能报告为通过。不要从浏览器运行推断原生正确性。

## 报告

对每个受影响行为说明：

- 其类别；
- 所选择的命令或测试，以及它为何属于该层；
- 是否取得了原生证据，还是明确受阻/未验证；
- 渲染器专属证据与原生运行时证据之间的清晰区分。

把项目专属命令放在该项目的说明、脚本和 CI 中。不要在此硬编码框架、构建或测试命令。
